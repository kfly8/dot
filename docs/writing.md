# dotの記事を書く

このブログは、kobaken（kfly8）の公開活動を紹介する。読者が「何を作っている人か」「その仕事が自分にどう役立つか」を具体的に理解し、作品やプロジェクトを試す入口にする。調査結果の羅列やdot自身の作業報告を記事の主題にしない。

初回記事の読者は、使うバックエンドを選びながらUIを作りたい開発者。公開資料とdotがツールを通じて確かめた実例を根拠にする。

## 執筆の流れ

1. 読後に持ち帰ってほしいことを一文にする。初回記事では「バックエンドを選ぶ自由と、人やAIが振る舞いを確かめる手段を一緒に育てている」。支える論点は2〜3点に絞る。
2. 公開可能な根拠を集める。環境、バージョン、コマンド、実際の出力を記録し、観察・資料の説明・解釈・未検証事項を区別する。私的会話や認証情報は残さない。公開リポジトリ中の未公開指定の文章も紹介根拠には使わない。
3. 日本語で、使う人に届く価値→それを支える実例→公開された開発の具体→試せる入口の順に書く。dotの評価と本人の発言は分け、本人の動機を創作しない。コード全文・操作ログ・詳細環境は検証資料へ寄せる。主題に必要なコマンドや因果関係を残し、一般論の導入や同じ主張の反復を減らす。
4. 技術的な確認後、誰が何をしたかが明確になるよう語順と文の長さを整える。自然な技術用語は保ち、長い補足は別の文へ移す。装飾のための強調は加えない。
5. 同じ根拠から英語版を書く。語順を機械的に移すのではなく、その言語で自然に伝える。限界と未検証事項も英語に残す。
6. 両言語のバージョン、数値、コード、リンク、主張、制約を照合する。ビルド後に切替リンクと実例をブラウザで確認する。

速度倍率、品質・安全性の保証、人間としての体験は、根拠なしに書かない。静的なテストを実行時テストやE2Eの代替と説明しない。
