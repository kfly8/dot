# dotの記事を書く

主役はプロダクト。読者の具体的な困りごとから、道具が何を助けるかを、再現できる例で示す。人物紹介やdotの作業日誌に主題を広げない。

初回記事の読者は、UIを実装したあとに値の接続を確かめたい開発者。持ち帰ることは「実行時・E2Eの前に、配線の一部を静的に確認できる」。次の行動は「小さな見積UIの接続を一つ変え、テストが差を検出するところまで試す」。

## 執筆の流れ

1. 読者の困りごと、持ち帰る一文、次に取る一つの行動を決める。主張を支える実例に絞り、無関係な人物情報・開発履歴・技術一覧は削る。
2. 公開可能な根拠を集める。環境、バージョン、コマンドと実出力を記録し、観察と解釈、未検証事項を分ける。私的会話や認証情報は載せない。
3. 正常系だけでなく、主張に対応した失敗例を確かめる。初回は子propの式を変え、同じテストの成功→失敗→復元後の成功を確認する。signal数だけで接続を検証したことにしない。
4. 日本語を、困りごと→仕組みと小さな例→再現手順→確認できる範囲の順に書く。本文には試すために必要なコマンドを残し、完全なコードと詳細ログは補足資料へ置く。フィードバックは具体的な疑問や不足を短く募る。
5. 主語と因果関係を明確にし、長い補足や同じ主張の反復を減らす。自然な技術用語を保ち、装飾の強調は加えない。
6. 同じ根拠から英語版を書き、数値・コード・リンク・制約を照合する。ビルドとテストを実行し、ブラウザで文章と実例、言語切替を確認する。

静的なテストを実行時・E2Eの代替と説明しない。根拠のない速度倍率や品質保証、人間の体験を装う表現は使わない。dotとkobakenの関係はAboutで簡潔に示す。
