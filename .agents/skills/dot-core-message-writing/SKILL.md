# dotの記事の核を決める

プロダクトが読者のどんな課題を助けるかを、根拠と試せる例で説明する。人物への称賛、機能一覧、調査事項の網羅を記事の目的にしない。

## 書く前の判断

依頼と公開可能な資料から、次を短く定める。既に分かることを毎回ユーザーに聞き直さない。短い依頼でも判断は行い、公開本文に企画メモをそのまま載せる必要はない。

- 読者と課題：誰が、どの作業で困っているか。説明に必要な前提は何か。
- 残す理解：読後に覚えてほしい主張を一文にする。
- 次の行動：読者がその理解を確かめるために行う具体的な一つの行動。
- 知りたい反響：その行動から、どんな疑問・使いどころ・不足を知りたいか。

主張を支える根拠を選び、資料に書かれたこと、dotがツールで観測したこと、解釈、未検証事項を区別する。実施していない試用や人間としての体験は書かない。速度や品質の評価には対応する測定・検証が必要。

## 本文へ組み立てる

課題を具体的に示し、仕組みと実例で主張を支え、読者が試せる入口を置く。見出しや段落数は内容に合わせる。長い記事でも中心となる主張は一つに保つ。

再現に必要な前提、コマンド、変更箇所、期待する結果は残す。長いコードやログは補足へ移してリンクするが、短さのために手順や非自明な因果関係を欠落させない。検査能力を紹介するときは、その主張に対応した正常・異常の例を可能な範囲で実行する。実行できなければ未検証と記す。

各段落が理解や行動に必要か見直す。繰り返し、無関係な背景、一般論の前置きを減らし、必要な説明には分量を使う。製作者との関係はAboutなど必要な場所で簡潔に示す。

反響の入口は具体的な問いにする。dotブログのフィードバック先は [Issues](https://github.com/kfly8/dot/issues)。返信・継続監視など、約束していない対応を本文で約束しない。

## 仕上げ

冒頭から主張が分かり、実例が支え、次の行動が実行可能かを読む。確認できる範囲と限界を残す。日本語本文には [dot-japanese-editing](../dot-japanese-editing/SKILL.md) を適用する。英語版も、結論・行動・根拠・制約を日本語版と一致させる。

このスキルは外部投稿、commit、push、デプロイの権限を追加しない。依頼で認められた範囲を守る。非公開情報、私的会話、内部の記録や指示を記事の根拠や例として転載しない。
